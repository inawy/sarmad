# وثيقة متطلبات المنتج — سرمد

## 1. تعريف المنتج

سرمد صفحة إهداء رقمية واحدة يستطيع الزائر تخصيصها باسمه أو باسم شخص آخر، ثم مشاركتها كرابط أو ملف صورة أو PDF أو طباعتها.

**الوعد الأساسي:** أنشئ صفحة إهداء باسمك أو باسم من تحب، وشاركها بسهولة.

سرمد ليس تطبيقًا للأذكار أو الأوراد. هذه منتجات مستقلة، ولا تدخل في نطاق هذا الإصدار.

## 2. المشكلة والفرصة

يريد المستخدم إنشاء إهداء رقمي جميل وشخصي يمكن إرساله أو الاحتفاظ به دون إنشاء حساب أو التعامل مع أدوات تصميم معقدة.

سرمد يجعل التخصيص جزءًا من الصفحة نفسها: يكتب المستخدم الاسم في موضعه داخل التصميم، ثم يشارك النتيجة.

## 3. الجمهور والاستخدامات

- شخص يريد إنشاء صفحة باسمه.
- شخص يريد إهداء الصفحة لشخص عزيز.
- شخص يريد مشاركة إهداء رقمي عبر تطبيقات التواصل.
- شخص يريد الاحتفاظ بنسخة قابلة للطباعة.

لا نفترض أن كل إهداء مرتبط بالوفاة؛ لذلك تكون الصياغة الافتراضية عامة ومحايدة، ويمكن لاحقًا إضافة قوالب أو عبارات اختيارية بعد اعتمادها.

## 4. تجربة المستخدم الأساسية

### أ. الصفحة العامة — دون اسم في الرابط

1. يفتح الزائر الصفحة.
2. يرى هوية سرمد وتصميم الإهداء نفسه.
3. يظهر موضع الاسم بدعوة مثل: «اكتب اسمك هنا أو اسم شخص عزيز تهدي إليه ثواب القراءة».
4. يضغط على موضع الاسم أو يبدأ الكتابة فيه.
5. يتغير الاسم داخل البطاقة مباشرة.
6. تظهر خيارات مشاركة الإهداء.

### ب. صفحة مخصصة — يوجد اسم في الرابط

1. يفتح الزائر رابطًا يحتوي على معامل `to`.
2. يقرأ التطبيق الاسم ويعرضه مباشرة في موضع الاسم.
3. لا تظهر دعوة إدخال الاسم بدل الاسم المخصص.
4. يستطيع الزائر تعديل الاسم أو بدء إهداء جديد.
5. يستطيع مشاركة الرابط أو تصدير البطاقة.

### ج. المشاركة والتصدير

- مشاركة الرابط باستخدام Web Share API عند توفرها.
- نسخ الرابط كبديل.
- تصدير البطاقة كصورة PNG.
- إنشاء PDF مناسب للحفظ والطباعة.
- فتح نافذة الطباعة مع تنسيق مخصص.

## 5. نطاق MVP

### داخل النطاق

- صفحة واحدة Responsive، عربية RTL أولًا.
- تصميم عام واحد لبطاقة الإهداء.
- اسم قابل للتحرير مباشرة داخل موضعه في البطاقة.
- قراءة الاسم من `?to=` وتحديث الرابط باستخدام History API دون إعادة تحميل الصفحة.
- مشاركة الرابط ونسخه.
- تصدير PNG.
- تصدير PDF.
- طباعة CSS.
- حالات تحميل/نجاح/خطأ واضحة وغير مزعجة.
- نشر Static على GitHub Pages.
- تعليمات وصول واستخدام لوحة المفاتيح.

### خارج النطاق حاليًا

- تطبيق الأذكار أو الأوراد.
- الحسابات وتسجيل الدخول.
- قاعدة البيانات أو Backend.
- حفظ صفحات المستخدم على خادم.
- لوحة تحكم أو إدارة محتوى.
- قوالب متعددة.
- إحصائيات وزيارات وتتبع.
- معاينات Open Graph ديناميكية لكل اسم.
- نظام مدفوع أو اشتراكات.

## 6. البيانات والرابط

### البيانات الأساسية

- `to`: اسم صاحب الإهداء، نص اختياري.
- لا تُضاف بيانات أخرى إلى الرابط في MVP إلا بقرار منتج لاحق.

### قواعد الاسم

- إزالة المسافات الزائدة من البداية والنهاية.
- السماح بالعربية واللاتينية والمسافات وعلامات الترقيم المعتادة.
- وضع حد معقول للطول لمنع كسر التصميم (اقتراح أولي: 60 حرفًا).
- عرض الاسم كنص React عادي، وعدم تفسيره كـ HTML.
- التعامل الآمن مع الروابط المشوهة أو قيمة `to` الفارغة.
- استخدام `URLSearchParams` في القراءة والكتابة.
- عدم تخزين الاسم على خادم. الرابط نفسه يحتوي على الاسم، لذلك يجب توضيح أن من يملك الرابط يستطيع رؤيته ومشاركته.

## 7. المشاركة والملفات

### الرابط

- بناء الرابط من عنوان الصفحة الحالي ومعامل `to`.
- استخدام `navigator.share` عند توفره.
- fallback إلى نسخ الرابط.
- لا ندّعي أن معاينة WhatsApp ستعرض الاسم ديناميكيًا؛ HTML المستضاف على GitHub Pages ثابت، وReact يحدّث المحتوى بعد فتح الصفحة.

### PNG

- تصدير عنصر البطاقة فقط، دون أزرار التحرير أو أدوات المشاركة.
- أبعاد مشاركة مستهدفة: 1080×1350 (نسبة 4:5).
- انتظار تحميل الخطوط والصور قبل الالتقاط.
- اختبار النص العربي واتجاه RTL في الناتج.

### PDF

- مقاس A4 مع هوامش مناسبة.
- الحفاظ على نسبة البطاقة وعدم قص النص.
- يمكن أن يكون PDF مبنيًا على صورة عالية الدقة في MVP؛ يجب توضيح أن النص لن يكون قابلًا للتحديد والبحث إذا استخدمنا هذا الأسلوب.

### الطباعة

- تنسيق `@media print` يخفي أدوات التحرير والمشاركة.
- خلفية وألوان مناسبة للطباعة، مع ضبط الهوامش.

## 8. نصوص المحتوى

- لا تُضاف آيات أو أحاديث أو أذكار في MVP دون تحديد المصدر ومراجعة النص.
- لا نستخدم عبارة «صدقة جارية» تلقائيًا لكل صفحة.
- الصياغة الافتراضية عامة، مثل «إهداء» و«إلى».
- أي عبارة تنسب ثوابًا أو حكمًا شرعيًا يجب أن تعتمد قبل النشر، ولا يصوغها التطبيق على أنها فتوى.

## 9. متطلبات الجودة

- Mobile-first.
- RTL صحيح في جميع أحجام الشاشة.
- سريع وخفيف ويعمل كصفحة Static.
- لا أخطاء Console في المسارات الأساسية.
- أزرار واضحة وحالات تركيز مرئية.
- تباين مناسب للنصوص.
- لا يعتمد نجاح المشاركة على وجود Web Share API.
- لا تضيع قيمة الاسم عند التصدير أو تحديث الرابط.
- يعمل الرابط المخصص عند إعادة فتحه أو إرساله إلى جهاز آخر.

## 10. معايير قبول MVP

- الصفحة العامة تعرض دعوة كتابة الاسم داخل بطاقة الإهداء.
- إدخال الاسم يحدّث البطاقة فورًا.
- نسخ/مشاركة الرابط ينتج رابطًا يعيد فتح الصفحة بالاسم الصحيح.
- الرابط المخصص يعرض الاسم فور التحميل.
- تعديل الاسم يحدّث رابط المشاركة.
- PNG مطابق للبطاقة المرئية ولا يتضمن أدوات التحكم.
- PDF يفتح ويطبع دون قص.
- الطباعة لا تتضمن الأزرار.
- التجربة الأساسية تعمل دون Backend أو حساب.
